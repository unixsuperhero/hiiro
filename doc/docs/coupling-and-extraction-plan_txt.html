    ⏺ Take a look at both. Key differences:

    sqlite3 gem — low-level:
db = SQLite3::Database.new("hiiro.db")
db.execute("SELECT * FROM todos WHERE status = ?", ["active"])
# => [["abc123", "fix bug", "not_started", ...]]  (plain arrays)

sequel gem — higher-level ORM:
DB = Sequel.sqlite("hiiro.db")
DB[:todos].where(status: "active").all
# => [{id: "abc123", text: "fix bug", status: "not_started", ...}]  (hashes)

Sequel pros for this project: named-column hash results (not positional
arrays), chainable queries, schema migrations built-in, no raw SQL for common
ops. The sqlite3 gem is its underlying driver anyway.

Given that we have ~15 tables and complex query patterns (filters, sorts,
joins for tasks/branches/PRs), Sequel would meaningfully reduce boilerplate.
But it's a heavier dependency.

★ Insight ─────────────────────────────────────
The HIIRO_INVOCATION_ID pattern is the cleanest way to link dispatch hops
across exec() boundaries — bin/h generates an ID and exports it as an env var
before exec'ing bin/h-branch, which reads it to attach its resolution to the
same parent record. No IPC needed, just a shared env var flowing through the
process tree.
─────────────────────────────────────────────────

My recommendation for the resolution design:

// Invocation — one per shell command entered
{ id: "inv_abc", command: "h branch saved", pwd: "/Users/josh/work/oncall",
  task: "oncall", worktree: "oncall/main", git_branch: "sa-form-...",
entered_at: "..." }

// InvocationResolution — N per invocation, ordered by depth
{ invocation_id: "inv_abc", depth: 0, bin: "h",        subcmd: "branch", args:
 ["saved"] }
{ invocation_id: "inv_abc", depth: 1, bin: "h-branch", subcmd: "saved",  args:
 []        }

Why this wins over single-record: you get the human-readable command (h branch
 saved) for display/search, AND the precise execution context for debugging.
depth: 0 always reflects what the user typed.

★ Insight ─────────────────────────────────────
The HIIRO_INVOCATION_ID pattern is elegant because environment variables are
inherited by child processes through exec() — the OS handles the propagation
for free. This is the same mechanism used by tools like RACK_ENV, NODE_ENV,
etc. to share context across process boundaries without any IPC machinery.

Sequel::Model's one_to_many + many_to_one associations are declared at the
class level and generate query methods like invocation.resolutions and
resolution.invocation — similar to Rails' has_many/belongs_to but without the
AR global state. Each association is explicit and composable.

★ Insight ─────────────────────────────────────
The before_create hook pattern used in TodoItem is a Sequel lifecycle callback
 — it fires automatically before any INSERT, so you don't have to remember to
set timestamps in every create call. It's equivalent to ActiveRecord's
before_create callback but purely opt-in per-model rather than inherited from
a base class.

The delete-all + re-insert save strategy in TodoManager is the simplest
correctness guarantee for in-memory lists: you never have stale rows from
deleted items. The trade-off vs. upsert-per-row is that it's a heavier write,
but for a personal todos list with <1000 items this is irrelevant — SQLite
handles it in microseconds.

    ⏺ Yes — dual-write. Every mutation writes to SQLite first (primary store), then

    rewrites the original YAML file as a backup. The YAML files stay live and in
sync, not just renamed.

The one-time auto-migration on first run (when hiiro.db doesn't exist yet)
goes the other direction: it reads the existing YAMLs → imports into SQLite →
renames each source to .yml.bak. After that, all subsequent writes go
DB-primary + YAML-backup.

So the flow is:

First run (no hiiro.db):
  YAMLs → [import] → hiiro.db
  YAMLs → renamed to .yml.bak

Every run after:
  Reads  ← hiiro.db (primary)
  Writes → hiiro.db + .yml (dual-write backup)

The .yml backups let you roll back to YAML-only if something breaks, without
losing any data written after migration.

    ⏺ This is a real architectural problem, and it’s worth being direct about it.

    The root issue: hiiro's bin files are doing 4 different jobs at once —

bin/h-branch:
  1. Parse args               ← orchestration
  2. Query git / tmux state   ← side effects
  3. Transform / decide       ← domain logic
  4. Print output             ← presentation
  5. Write to files/DB        ← persistence

When all 5 are interleaved in one block, there's nothing to test that doesn't
also require a terminal, a tmux session, or a real git repo.

The SQLite migration actually helps here — the models are now the cleanest
layer in the codebase and are trivially testable:

# test setup — in-memory DB, no files, no fixtures
def setup
  @db = Sequel.sqlite
  Hiiro::DB.instance_variable_set(:@connection, @db)
  Hiiro::TodoItem.create_table!(@db)
end

def test_active_todos
  Hiiro::TodoItem.create(text: "Fix bug",    status: "not_started")
  Hiiro::TodoItem.create(text: "Ship thing", status: "done")
  assert_equal 1, Hiiro::TodoItem.where(status: "not_started").count
end

No YAML, no filesystem, runs in microseconds.

The presentation mixing is the harder problem. Something like
PinnedPRManager#display_pinned is 60 lines of ANSI/formatting logic —
completely untestable and it lives right next to the query logic.

A few options for how to handle this going forward:

Option A — Incrementally extract presenters as we touch files
When a file gets a Sequel model anyway, also extract its display methods into
a Presenter class. No big-bang refactor, just enforce the rule going forward.

Option B — Write tests only for the model/domain layer, skip bin files
Accept that bin files are thin orchestrators and only test what's actually

the side-effect-heavy bin files.

Option C — Define a Hiiro::Effects interface
Create an injectable adapter for side effects (tmux calls, git calls, exec).

full coverage.

   Option C: Hiiro::Effects Injectable Interface

   Context

   Hiiro's test suite is hard to maintain because side effects (tmux, git,
   filesystem, process exec) are
   interleaved with domain and presentation logic in bin files and manager
   classes. Claude has repeatedly
   mixed these concerns, making tests brittle or impossible to write.

   The good news: Hiiro::Tmux and Hiiro::Git already have an internal adapter
   pattern — they route
   all calls through three private methods: run_safe (backtick), run_system
   (system), run_success?
   (silent system). The gap is that these aren't injectable, so tests can't
   substitute them.

   Goal: Make side effects injectable via a Hiiro::Effects namespace. Real
   code gets real
   implementations; tests get lightweight doubles. No new abstraction layers —
    just expose and inject
   what already exists.

   Not a big-bang rewrite. This is incremental: start with Tmux and Git
   (highest test value), then
   add Filesystem and Process. Each step is independently useful.

   Step 1: Define the Effects interfaces (lib/hiiro/effects.rb)

   Three interfaces, each with a real implementation and a test double:

   module Hiiro
     module Effects
       # Wraps backtick + system calls for tmux and git
       class Executor
         def capture(*args)  = `#{args.shelljoin} 2>/dev/null`
         def run(*args)      = system(*args)
         def check(*args)    = system(*args, out: File::NULL, err: File::NULL)
       end

       # Test double — records calls, returns configured stubs
       class NullExecutor
         attr_reader :calls

         def initialize
           @calls   = []
           @stubs   = {}
         end

         def stub(pattern, output)
           @stubs[pattern] = output
         end

         def capture(*args)
           @calls << { method: :capture, args: args }
           find_stub(args) || ""
         end

         def run(*args)
           @calls << { method: :run, args: args }
           find_stub(args).nil? ? true : find_stub(args)
         end

         def check(*args)
           @calls << { method: :check, args: args }
           find_stub(args).nil? ? true : !!find_stub(args)
         end

         def called?(pattern)
           @calls.any? { |c| c[:args].any? { |a| a.to_s.include?(pattern.to_s)
    } }
         end

         private

         def find_stub(args)
           key = args.map(&:to_s).join(' ')
           @stubs.find { |pat, _| key.include?(pat.to_s) }&.last
         end
       end

       # Filesystem effects (read/write/delete)
       class Filesystem
         def write(path, content)    = (FileUtils.mkdir_p(File.dirname(path));
    File.write(path, content))
         def read(path)              = File.read(path)
         def exist?(path)            = File.exist?(path)
         def mkdir_p(path)           = FileUtils.mkdir_p(path)
         def rm(path)                = File.delete(path) if File.exist?(path)
         def mv(src, dst)            = FileUtils.mv(src, dst)
         def glob(pattern)           = Dir.glob(pattern)
       end

       class NullFilesystem
         attr_reader :writes, :deletes

         def initialize
           @store   = {}
           @writes  = []
           @deletes = []
         end

         def write(path, content)    = @writes  << path and @store[path] =
   content
         def read(path)              = @store[path] || raise(Errno::ENOENT,
   path)
         def exist?(path)            = @store.key?(path)
         def mkdir_p(path)           = nil
         def rm(path)                = @deletes << path and
   @store.delete(path)
         def mv(src, dst)            = @store[dst] = @store.delete(src)
         def glob(pattern)           = @store.keys.select { |k|
   File.fnmatch(pattern, k) }
       end
     end
   end
