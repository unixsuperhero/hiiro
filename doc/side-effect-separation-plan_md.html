    This is a really interesting architectural problem. Let me think about what the right approach is.

    The core problem: - Commands like h branch saved do: git operations, tmux operations, file writes, terminal output — all interleaved - Sequel models help somewhat (DB operations are more testable), but the bin files still mix everything

    • The Hiiro::TestHarness stubs system calls but that’s limited

    The real solution is separating concerns: pure domain objects that return values without I/O, a store layer using Sequel for testable database access, presenters that format domain objects into strings, and isolated side-effect executors for tmux, git, and process calls that can be stubbed at the boundary.

    The current codebase mixes everything together—bin files orchestrate and execute, models like TodoItem blend formatting with domain logic, and PinnedPRManager handles display, API calls, file writes, and business logic in one place.

    The SQLite migration actually improves testability significantly because the store layer is now real and testable with an in-memory database, making queries like TodoItem.where(status: ‘active’) verifiable without file fixtures.

    I should recommend extracting presenters for display logic, creating service or command objects for domain operations separate from bin file orchestration, and keeping side effects isolated and minimal so they’re easy to stub in tests.

    ⏺ This is a real architectural problem, and it’s worth being direct about it.

    The root issue: hiiro’s bin files are doing 4 different jobs at once —

    bin/h-branch: 1. Parse args ← orchestration 2. Query git / tmux state ← side effects 3. Transform / decide ← domain logic 4. Print output ← presentation 5. Write to files/DB ← persistence

    When all 5 are interleaved in one block, there’s nothing to test that doesn’t also require a terminal, a tmux session, or a real git repo.

    The SQLite migration actually helps here — the models are now the cleanest layer in the codebase and are trivially testable:

    # test setup — in-memory DB, no files, no fixtures def setup @db = Sequel.sqlite Hiiro::DB.instance_variable_set(:@connection, @db) Hiiro::TodoItem.create_table!(@db) end

    def test_active_todos Hiiro::TodoItem.create(text: “Fix bug”, status: “not_started”) Hiiro::TodoItem.create(text: “Ship thing”, status: “done”) assert_equal 1, Hiiro::TodoItem.where(status: “not_started”).count end

    No YAML, no filesystem, runs in microseconds.

    The presentation mixing is the harder problem. Something like PinnedPRManager#display_pinned is 60 lines of ANSI/formatting logic — completely untestable and it lives right next to the query logic.

    A few options for how to handle this going forward:

    Option A — Incrementally extract presenters as we touch files When a file gets a Sequel model anyway, also extract its display methods into a Presenter class. No big-bang refactor, just enforce the rule going forward.

    Option B — Write tests only for the model/domain layer, skip bin files Accept that bin files are thin orchestrators and only test what’s actually testable — the Sequel models, matchers, option parsing. Stop trying to test the side-effect-heavy bin files.

    Option C — Define a Hiiro::Effects interface Create an injectable adapter for side effects (tmux calls, git calls, exec). Bin files get effects: injected; tests pass a double. Most invasive but gives full coverage.

    Given that the test suite is already out of date and hiiro is a personal CLI tool, I’d suggest Option B as baseline + Option A opportunistically. Write solid tests for the model layer (which is now genuinely clean), and extract presenters when you’re already editing a file for another reason.
